# 大世界地图改造设计：从 11 节点到搜打撤沙盒

> 日期：2026-10-10
> 目标：把现有 11 节点网格，扩成你设想的「骑马与砍杀 + 搜打撤 + 修仙阁」的完整体验
> 约束：零构建、原生 ESM、n0–n10 的 ID 必须不变（5 条叙事线 + 8 条支线硬编码引用）

## 一、先说清楚现状：你想要的和现有的差多远

### 1.1 现有地图的全部家当（实测）

`js/xiuxian/world.js`，**99 行**：

|---|---|
| 节点数 | **11**（n0–n10） |
| 网格 | x,y ∈ [1,4]，实际 3 行 × 4 列 |
| 边 | **15 条**（曼哈顿距离==1 自动生成） |
| 节点类型 | 5 种：village(2) / field(5) / elite(2) / secret(1) / boss(1) |
| 最小度数 | 2（无死胡同） |
| 赶路成本 | `travel()` 恒定 `cost:1`，**无距离概念** |
| 路上遭遇 | **无** |
| 区域概念 | **无**（`WORLD.grid=6` 但坐标只到 4，是历史遗留 bug） |
| 篝火上限 | **3 处** |
| 领地槽位 | 6 格起，随 TIERS 晋升增加 |
| 撤离点 | **无**（全库 0 次出现"撤离"） |

### 1.2 逐条对照你的设想

| 你的设想 | 现状 | 差距 |
|---|---|---|
| 大世界地图（区域/城镇/宗门） | 11 节点 5 类型，无区域层 | **缺「区域」这一层** |
| 骑马与砍杀（赶路/遭遇/队伍/雇佣） | `travel()` cost:1，相邻即到 | **无距离、无路上遭遇、无队伍** |
| **搜打撤（带进去/带不出来）** | 无撤离概念，局末必定落袋 | **整个机制缺失** |
| 砍杀 = 日常搜集历练 | ✅ 已成立 | 无需改 |
| 主线在地图（幻境/副本/剧情） | 1 妖巢 + 1 秘境 + 2 险地 | 副本少，**无幻境** |
| 种田（灵田开垦开荒） | 灵田有，10 分钟一熟 | ✅ 有产出，**无「开垦」过程** |
| 据点 / 篝火 | 篝火≤3，领地 6 格起 | ✅ 机制全，**池子太小** |
| 黑白夜 | 晨/昼/暮/夜，**只改倍率** | **无环境危害** |
| 伙伴/仆从/雇佣/结伴 | 灵伴 3 形 + 酒馆同伴 | 无雇佣、无仆从 |
| 商会 / 行会 | `market` 有交易 | **无行会** |
| 奇遇 / 守卫 | `ENCOUNTERS` 7 个（在洞府，非地图） | 奇遇**不在地图上** |

### 1.3 一个重要发现：现有是「双层结构」

领地/矿脉/灵田/篝火**不是**地图节点的一部分，而是**绑在 nodeId 上的第二套图层**：

```js
// build.js:357
MINE_TIER: { secret:3, elite:2, boss:3, field:1, village:0 },
canClaimMine(nodeId) {
  if (this.s.fires.some(f => f.nodeId === nodeId)) return {ok:false, msg:'此处分给你建篝火了。'};
  ...
}
```

**篝火和矿脉互斥，争抢同一批 11 个节点。** 村庄无矿（`village:0`），所以"占领村庄"在矿脉系统里没有价值。

**这个双层结构其实是对的** —— 地图（世界）和领地（你的地盘）分离，扩展时不必推翻它。但节点池从 11 扩到 60+ 之后，"篝火 ≤3 处争抢 60 个节点"就会失去意义（篝火放哪都一样）。**扩节点时必须同步扩领地/篝火的语义。**

## 二、核心设计问题：搜打撤 和 Roguelite 是冲突的

这是整个改造里**必须先想清楚的一件事**，不然会做出一个不好玩的东西。

### 2.1 冲突的本质

| | 现有砍杀局（Roguelite） | 搜打撤（Tarkov 式） |
|---|---|---|
| 死亡损失 | **只损失时间**（`d.gold += s.gold` 照给） | **损失资产**（携带物全丢） |
| 局外资产 | 稳增 | 波动 |
| 心理预期 | 「多跑几局变强」 | 「这一趟能活着出来吗」 |
| 适合频率 | 一天 5–10 局 | 一天 1–2 局 |

**直接照搬 Tarkov 会摧毁这个游戏。** 玩家一天跑 10 局、死 3 局，一天白玩，第二天就不来了。

### 2.2 我的解法：**双轨制**

**关键洞察：你的两个玩法诉求本身是不同频次的。**

- 「砍杀是日常搜集和修炼历练」→ **高频**，每天几十次，要爽、要快、死了不心疼
- 「主线是地图上的幻境、副本、剧情」→ **低频**，一天 1-2 次，要有风险、有记忆点

**所以搜打撤机制应该只挂在「副本/幻境/秘境深入」上，不挂在日常砍杀上。**

```
日常砍杀局（高频，零风险）
  ├─ 死亡：时间损失，金币照给 ← 保持现状不动
  └─ 定位：稳定产出、练手、刷神通等级

副本 / 幻境 / 秘境深入（低频，搜打撤）
  ├─ 出发前：在据点装载物资（丹药/符箓/工具），受背包容量限制
  ├─ 进入：拿到的战利品先进「战利品栏」，不是背包
  ├─ 撤离：必须走到撤离点（篝火/传送阵/村口）才算带出
  └─ 死亡：战利品全丢，装载的物资可能损失一部分（按保险机制）
```

**这样既有了搜打撤的张力，又不破坏日常循环。**

### 2.3 三个降低挫败感的设计

**① 保险（借鉴 Tarkov，但只保底不保赚）**
```
出发前可为「丹药/符箓」投保（花少量保费）
死亡时：投保部分返还 60-80%，未投保全丢
不可保险：稀有材料、传承书、神通卷轴 ← 这是真正的赌注
```

**② 撤离点可见**
地图上撤离点（篝火、传送阵、村口）常驻显示，让玩家有明确的"往哪跑"目标。**搜打撤的张力来自"距离撤离点还有多远"，不是来自"不知道能不能出去"。**

**③ 层级风险**
```
浅层秘境：低危，物资少，撤离容易  → 练手
中层：中等                          → 正经跑
深层（幻境）：高危，物资多，撤离点远 → 高风险高回报
```
玩家自己选深度。**这比"一刀切的高死亡惩罚"友好得多。**

## 三、扩展的四个阶段

每个阶段都能独立发布，**不破坏现有内容**。

### 阶段 0：修基础（0.5 天）
- 修 `WORLD.grid = 6` 但坐标只到 4 的 bug
- 节点数据从 `world.js` 抽到独立的 `map-data.js`（保持 n0–n10 不变）
- 加 `lint-map.mjs`：断言所有 `story.js`/`quest.js` 引用的 nodeId 都存在

**这是所有后续工作的前提** —— 现在没有任何 lint 保证节点 ID 有效，加节点时很容易打断剧情线。

### 阶段 1：加「区域」层（3-5 天）

引入区域概念，节点归属区域：

```
苍梧界（总）
├── 青石村域（安全区，2 村 1 野）
├── 黑风岭域（散修争夺，险地为主，矿脉富集）
├── 落云镇域（坊市，行会总部，商队枢纽）
├── 古战场域（高危，妖巢，副本）
└── 秘境域（青岚秘境，幻境入口）
```

**区域属性**：`势力归属 / 危险等级 / 资源类型 / 昼夜影响 / 是否禁战 / 通行费`

**这是「网」的骨架** —— 区域之间的通行规则（通行费、势力关系、封锁状态）创造了真正的空间感。

### 阶段 2：赶路与遭遇（3-5 天）

把 `travel()` 从「相邻 cost:1」升级为「距离 × 道路类型 × 遭遇」：

```js
travel(from, to) → {
  cost: 计算距离（不再是 1）,
  roadType: '官道' | '野路' | '捷径',
  encounters: [遭遇事件...],   // 按距离和危险度生成
  blocked: null | { reason, until }   // 封锁状态
}
```

**路上的遭遇**（骑马与砍杀的核心）：不是进节点才有事，而是**在赶路途中出事**。雾劫、商队冲突、路遇修士、发现矿脉……

### 阶段 3：搜打撤（5-8 天）
见第二节的「双轨制」设计。核心是：
- 战利品栏（局内，撤离才落袋）
- 装载（出发前，受容量限制）
- 撤离点
- 保险机制

### 阶段 4：领地与据点（5-8 天）
- 篝火从 3 处扩到按区域分布
- 据点建设（不再是"格子"，而是"占地"）
- 灵田开垦（从"有产出"到"有开垦过程"）

## 四、体量控制：什么该做，什么不该做

这是 1-3 人团队最需要知道的部分。

### 4.1 🔴 绝对不要做

| 系统 | 为什么砍 |
|---|---|
| 实时大地图（自由行走） | 破坏 Canvas 2D 的现有性能预算；骑马与砍杀的核心是"节点+赶路"，不是"骑马" |
| 复杂 NPC 关系网 | 现有的 3 人物 + 5 叙事线已经够写；再加人物只会稀释每个 |
| 程序化世界生成 | 手工设计的 11 个节点已经跑通；程序化在这个体量是负收益 |
| 多派系战争 | 需要 AI 决策 + 大量平衡，1-3 人做不完 |
| 载具/坐骑移动 | 视觉收益大，机制收益小 |
| 完整的搜打撤保险系统 | 先做"能带出/带不出"就够了，保险是锦上添花 |

### 4.2 🟡 最小可行版本（20% 工作量）

**如果只做这些，能得到什么体验：**

```
1. 区域层（3 个区域，不是 5 个）
2. 赶路消耗 + 路上遭遇（每个区域 3-4 种遭遇）
3. 秘境「深入」模式 = 唯一的搜打撤场景
4. 撤离点：篝火 + 村口
5. 战利品栏 + 死亡全丢
```

**这 5 项的体验已经很完整**：玩家有了"选择去哪、多远、带什么、能不能出来"的核心决策。

**预估代码量**：1200-1600 行（约占现有 23698 行的 6-7%）

### 4.3 阶段 1-3 的代码量估算

| 阶段 | 新增文件 | 估算行数 | 风险 |
|---|---|---|---|
| 0 修基础 | 2 | ~150 | 低 |
| 1 区域层 | 2 | ~400 | 低（纯数据） |
| 2 赶路遭遇 | 2 | ~500 | 中 |
| 3 搜打撤 | 2-3 | ~700 | **中高**（要改 startRun/endRun） |
| 4 领地据点 | 2 | ~600 | 中 |
| **合计** | **10-11** | **~2350** | — |

**关键：阶段 0-2（1050 行）是低风险的纯数据扩展，可以立刻做。阶段 3 才是真正要动核心的。**

## 五、必须保持的约束

### 5.1 节点 ID 绝不能变

5 条叙事线的 `beats` 硬编码了 nodeId：
```
hongyi:  n0 → n0 → n4 → n5
laolao:  n9 → n7 → n5 → n5
tomb:    n8 → n8 → n8 → sj
jiangu:  n8 → n8 → n8 → n8
auspicious: n2 → n2 → n4 → n4
```

8 条支线的 `QUEST_COND.where` 也引用：n10, n1, n5, n7, n2, n8, n3, n4

**扩展地图时，n0–n10 必须全部保留，类型可以改，ID 不能改。** 新节点用 n11 起编。

### 5.2 `startRun` 的签名要扩展

现在：
```js
function startRun(charId) { ... }
```

搜打撤需要：
```js
function startRun(charId, loadout) {
  // loadout: { mode:'daily'|'extract', loot:[], insured:{}, target:nodeId }
}
```

**向后兼容**：`loadout` 省略时行为与现在完全一致。**这样日常砍杀局零改动。**

### 5.3 局末结算要分叉

现在 `endRun` 无条件落袋。搜打撤模式要：
```js
if (loadout?.mode === 'extract') {
  if (extractSuccess) { 落袋全部战利品 }
  else { 战利品全丢，按保险返还部分物资 }
} else {
  现有逻辑不变   // daily 模式
}
```

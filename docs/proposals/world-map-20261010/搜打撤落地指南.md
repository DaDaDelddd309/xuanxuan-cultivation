> 配套：《大世界地图改造设计》第二节
> 面向：1-3 人团队，基于现有 23698 行代码扩展
> 所有约束均基于实测的现有代码结构

## 陷阱 1：把搜打撤套在日常砍杀上

### ❌ 错误做法
所有砍杀局都改成"带物资进去，死了全丢"。

### 后果
砍杀局是**日常重复玩法**（README 写明「这是主要的时间消耗」），玩家一天 5-10 局。搜打撤式死亡惩罚 = 一天死 3 次 = 一天白玩。

**第二天玩家就不来了。**

### ✅ 正确做法：双轨制

| 轨道 | 频率 | 死亡惩罚 | 定位 |
|---|---|---|---|
| **日常砍杀** | 5-10 次/天 | **只损失时间**（现状不变） | 稳定产出、练手、刷神通 |
| **副本/幻境/秘境深入** | 1-2 次/天 | **战利品全丢** | 高风险高回报、记忆点 |

**搜打撤机制只挂在低频副本上。** 这样既有张力，又不破坏核心循环。

### 代码落点
```js
// main.js:303 —— 向后兼容，daily 模式零改动
function startRun(charId, loadout) {
  // loadout 为 undefined → 现有行为完全不变
  const mode = loadout?.mode || 'daily';
  ...
}
```

## 陷阱 2：没有"战利品栏"这个中间态

### ❌ 错误做法
局内捡到的东西直接进 `Bag`（修仙阁行囊），局末直接落袋。

### 为什么致命
搜打撤的**全部张力来自"带不带走"**。如果东西直接进背包，玩家永远不需要做"要不要再贪一波"的决策——**没有决策就没有玩法**。

而且现有 `Bag` 是**无上限**的：
```js
// items.js:101
s: { items: {}, demon: 0, charter: false },
add(id, n = 1) { this.s.items[id] = (this.s.items[id] || 0) + n; return true; }
```
**无容量约束 = 无取舍 = 无张力。**

### ✅ 正确做法：三层结构

```
出发装载 (loadout)  →  局内战利品栏 (runLoot)  →  修仙阁行囊 (Bag)
   受容量限制            死了全丢                 最终资产
   可投保                撤离才转出
```

**局内战利品栏是必需的中间态。** 它在 `engine` 之外、`Bag` 之前。

### 代码落点
```js
// 新建 js/game/lootrun.js —— 局内战利品收集器
export const RunLoot = {
  items: [],        // 局内捡到但还没带出的
  cap: 20,          // 战利品栏容量（格数）
  add(id, n=1) { 
    if (this.items.length >= this.cap) return false;  // 满了就不捡
    ...
  }
};
```

**注意**：`engine.stats` 目前只有 `{ kills, gold, level, dmg }` 四个字段，**没有战利品清单**。必须新增。

## 陷阱 3：撤离点藏起来

### ❌ 错误做法
撤离点是隐藏的/随机的，玩家不知道能不能出去。

### 为什么致命
搜打撤的张力应该来自**"距离撤离点还有多远"**，不是来自"不知道能不能出去"。

隐藏撤离点 = 纯粹的运气惩罚 = 玩家无法通过决策改善结果 = **这不是策略，这是抽签**。

### ✅ 正确做法

**撤离点在地图上常驻可见**，并且有三档设计：

```
篝火（你的据点）    撤离安全，但只有 3 处，且需要篝火在烧
传送阵（领地 LV2+）  撤离快，但消耗传送次数/资源
村口/镇口            永远可用，但距离远
```

**玩家在局内能看到的**：一个"距离最近的撤离点在哪、还有多远"的 HUD 指示。

### 代码落点
```js
// world.js 新增
export const EXTRACT_POINTS = {
  n0: { type:'village', name:'青石村口', safe:true },
  n9: { type:'village', name:'落云镇口', safe:true },
  // 篝火点由 build.js 动态注册
};
// 副本内部另有撤离点
```

## 陷阱 4：一刀切的高死亡惩罚

### ❌ 错误做法
所有副本难度相同，死亡全丢。

### 为什么致命
新玩家第一个小时死 5 次，直接流失。老玩家才会玩刺激的。

### ✅ 正确做法：分层风险 + 保险

**① 分层**
```
浅层秘境：低危，物资少，撤离点近  → 练手，新手区
中层：    中等                       → 正经跑
深层幻境：高危，物资多，撤离点远    → 高风险高回报
```

**② 保险（只保底不保赚）**
```
出发前可为「丹药/符箓/消耗品」投保（花少量保费）
死亡时：投保部分返还 60-80%，未投保全丢
不可保险：稀有材料、传承书、神通卷轴  ← 这才是真正的赌注
```

**关键设计**：不可保险的那几样东西，恰好是**最有价值、也最舍不得带进去**的。这样每个玩家自己决定赌多大。

### 代码落点
```js
// js/xiuxian/insure.js
export const INSURE = {
  rates: { pill: 0.7, scroll: 0.6, stone: 0.0, charter: 0.0 },
  quote(itemId, n) { /* 返回保费 */ },
  claim(loadout) { /* 死亡时计算返还 */ },
};
```

## 陷阱 5：忽略了"营地"已有的互斥机制

### 现有约束（实测）
```js
// build.js:357
MINE_TIER: { secret:3, elite:2, boss:3, field:1, village:0 },
canClaimMine(nodeId) {
  if (this.s.fires.some(f => f.nodeId === nodeId)) {
    return {ok:false, msg:'此处分给你建篝火了。'};
  }
  ...
}
```

**篝火和矿脉互斥，争抢同一批节点。** 篝火上限 3 处，领地 6 格起。

### 扩展后的问题
节点从 11 扩到 60+ 之后：
- 「3 处篝火争抢 60 个节点」→ **篝火放哪都一样，无决策**
- 「村庄无矿（village:0）」→ 11 个节点里 2 个村庄对领地系统无价值

### ✅ 正确做法

扩展时同步给节点加**领地价值维度**：

```js
// 扩展后的节点 schema
{
  id: 'n23', x: 7, y: 4, type: 'town',
  name: '落云坊市',
  // 新增：领地/篝火相关
  land: {
    buildable: true,     // 能否建篝火
    mineTier: 0,         // 矿脉价值（0=无）
    farmTier: 2,         // 灵田价值 ← 你的"开垦"就靠这个
    popCap: 3,           // 人口上限加成
  },
}
```

**让不同节点在「建篝火 / 占矿脉 / 开灵田 / 驻人口」上各有优劣**，选址才有意义。

## 陷阱 6：把「开垦」做成一个按钮

### 你的设想
> 种田、开垦开荒、据点

### 现状
灵田**有产出，但无开垦过程**：
```js
// build.js:19
export const FIELD_PERIOD = 10 * 60 * 1000;   // 灵田 10 分钟一熟
```

### ❌ 错误做法
加一个「开垦灵田」按钮，点一下就建成。

### 为什么这样不对
"开垦"的核心不是**建成**，是**过程里有决策**：
- 选在哪块地（肥力/水源/朝向）
- 投入多少（人力/源石/时间）
- 承担什么风险（开垦期会不会被袭扰）

**这恰好和你的「据点 + 黑白夜 + 守卫」设想天然咬合。**

### ✅ 正确做法：开垦是一个「占用了节点的微型副本」

```
1. 选一块地（地图节点，需未被他占）
2. 投入资源（源石 + 族人手）
3. 开垦期：N 分钟，期间该节点会刷怪
   → 这就是一次「微型砍杀局」，死了开垦失败损失投入
4. 建成：获得持续的灵田/矿脉产出
```

**这样"开垦"天然获得了搜打撤的张力** —— 你投入的东西在开垦期间是暴露的。**不需要额外设计。**

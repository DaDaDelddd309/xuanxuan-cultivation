## 七、手持战利品局末销毁 —— **复现了「清空」，但不是玩家可见的损失**

报告说的链路我复现了：`_fetch` 把宝石从世界摘走存进 `carry`，
`begin()` 里 `this.carry = null`。合成世界跑出来确实是这样：

```
开局: 世界里宝石数 = 1  手上 carry = 无
捡起瞬间: 在手 = true  还在世界 = false  玩家经验 = 0
局末之后: 在手 = 无  还在世界 = false  玩家经验 = 0
>>> 宝石被永久销毁 = true
```

**但继续往下查，「销毁」不成立**：

```
engine.reset() → this.pickups.length = 0      ← 整个世界连同那颗一起清(实测 2 → 0)
main.js 的 startRun 里,engine.reset() 排在角色/灵伴初始化之前(实测 reset@185 / 灵伴@615)
```

顺序是「**世界先清空 → 再清 carry**」。所以 `carry = null` 没有额外损失任何东西，
玩家看不到少一颗 —— 报告那个探针是直接调 `_reset()` 并手工造的世界，没走真实 `startRun` 路径。

另外我查清了 `_reset()` 的**唯一**调用点是 `companion-gather.js:160`
（`!p || !this.actor.present` —— 她被打散/玩家不在），**不是局末**。
所以「把东西退回世界」这个修法绝不能塞进 `_reset()`：那会在她被打散时把物品瞬移回去。

**处置：不改行为，钉住前提。**
这个缺陷之所以被报成「凭空消失」，是因为没有任何测试钉住「让这件事安全的前提」。
已在 `tests/companion-gather-regression.mjs` 补 G8 两条：

1. `engine.reset()` 真的清空 `pickups`（**动态构造 Engine 跑**，不靠读源码猜）
2. `startRun` 里 `engine.reset()` 排在灵伴初始化之前（源码顺序断言）

双向注入验证：抽掉 `pickups.length = 0` → EXIT=1；把 reset 挪到灵伴之后 → EXIT=1；
还原后 EXIT=0、md5 一致。

> 补桩时踩了一下：G8 的动态断言一开始被 `ℹ️ 跳过动态断言` 掉了（环境缺 `window.addEventListener`）。
> **跳过的断言和没有断言一样是假绿**，所以补了 Engine 构造用到的那几个桩，现在 40 项 0 跳过。

## 十、音频系统审计复验（XX-AUDIT-023）

外部审计给了两条 P0 + 一条「顺带」+ 一条 P1。**三条结论我复现不出来，一条坐实。**

### 怎么测的（这部分比结论重要）

审计报告说自己是「数值仿真」：逐字复刻 `_tone` 的 `exponentialRampToValueAtTime` 包络。

我一开始也是这么干的（`$HOME/_audio*.mjs`），**结果第一版就把插值方向写反了** ——
`f=0`（刚 `setValueAtTime`）时返回了 ramp 的**末值**，整条包络是倒的，
所有读数偏小 3~5 倍，而我当时看着「数字挺合理」就往下推了。

所以最后换了个办法：**塞一个假 `AudioContext` 进 `audio.js`，记录 `GainParam` 的自动化事件，
从产品代码自己产出的事件里重建包络**。不重写公式，就没有抄错的可能。
（探针的 `voiceAt()` 沿 GainNode 链连乘到 `destination`，所以 `sfxBus`/`master`
的增益已经含在里面，外层**不能**再乘一次 —— 我第一版乘了两次，所有数都少 0.2 倍。）

自检口径：单发音效的峰值必须与手算逐项吻合。

```
shoot 0.2×0.2=0.040 ✅   hit 0.5×0.2=0.100 ✅   hurt (0.55+0.25)×0.2=0.160 ✅
coin 0.35×0.2=0.070 ✅   boss (0.65+0.40)×0.2=0.210 ✅   evolve 0.092 ✅
```

### P0-1「团战削波」—— **证据错，缺陷不存在**

> 报告原话：`spawner` 允许一次 50 只同帧死，`enemies.js:324` 就会连发 50 次 `hit`，
> 累计 **5.0（+14 dBFS）** 硬削波。

`SFX.play()` 里有一张**按名字**的全局节流表 `GAPS`（`audio.js:7-11`，`hit: 40`）。
它管的是**所有** emit 方 —— 不管调用方自己有没有节流。
所以「50 次同帧 hit」在代码里跑不出来：

```
同帧 emit 100 次 hit → 实际发声 1 个声部，总线峰值 -20.0 dBFS
```

顺带纠一处我自己的标注：`enemies.js:324` 是 `bomberBoom()`（火药童子自爆），
不是 `killEnemy()`。三个 `hit` emit 点里，195 行（普通命中）有 70ms 节流，
216（蒸汽爆发）和 324（殉爆）没有 —— 但它们共用 `GAPS.hit`，所以不构成叠加。

**真正值得看的数字不是「会不会削波」，是余量。** 我按真实密度跑了一个两秒团战
（每帧 shoot+hit，每 4/7/11/3/9 帧各来 pickup/coin/hurt/dash/synergy）：

| 场景 | 总线峰值 | RMS |
|---|---|---|
| 2 秒真实团战（emit 840 次 → 260 个声部） | **-5.3 dBFS** | -18.9 |
| 每帧全 emit 的不可能事件 | -5.3 dBFS | -18.9 |
| 单发最响 `boss` | -13.6 dBFS | -27.4 |

**没削波，但只剩 5.3 dB 余量。** 所以我没有加 `DynamicsCompressor` ——
针对一个不存在的缺陷加限幅器，是拿一个不可逆的声音改动去换一个假红灯。
我改成把这个余量**变成门禁**：以后谁把某个 gain 乘大，它会红。

### P0-2「BGM 轻 20 dB，建议 `musicBus` 0.25 → 0.6」—— **建议有害，不采纳**

报告说 `0.25 × 0.2 = 0.05 → -45.7 dBFS`，比常见的 `-26 ~ -20` 轻 10~20 dB。

**-45.7 是单声部 RMS，却拿去和音效的峰值比。** 真跑 BGM 一个完整 8 步循环：

| musicBus | BGM 循环峰值 | BGM 循环 RMS | 对照单发音效峰值 |
|---|---|---|---|
| **0.25（现状）** | **-25.8 dBFS** | -40.9 | shoot -28.0 / pickup -25.0 / coin -23.1 / hit -20.0 / hurt -15.9 |
| 0.40 | -21.7 | -36.8 | 同上 |
| 0.60（报告建议） | **-18.2** | -33.3 | **比 coin 还响 4.9 dB，比 hurt 只差 2.3 dB** |

现状 0.25 落在 `shoot` 与 `pickup` 之间 —— 音乐在常规音效之下、
在 `hit`/`coin` 之下压得住，这是正常的混音关系。
按建议改 0.6 会让 BGM 盖住音效。

**「BGM 不可调」是真的，但修法不是猜一个常数。** 那是设置面板没有音量滑块的问题，
属于功能缺口；写死一个「对」的数值只是把猜测固化下来。

### 顺带一条「lowpass 1200 Hz 把旋律闷了，建议抬到 1800~2000」—— **不成立**

用 RBJ 公式算 `musicFilter`（fc=1200, Q=0.7）的真实幅频响应：

| 频率 | 增益 | 说明 |
|---|---|---|
| 659 Hz | **-0.42 dB** | `M_ARP[1]/[3]` |
| 698 Hz | **-0.52 dB** | `M_ARP[5]` |
| 1976 Hz | **-9.33 dB** | 原 square 基频的三次谐波 = **蜂鸣源** |

琶音音高被削掉 0.4~0.5 dB，听不出来。抬到 2000 只回收 0.35 dB，
却把蜂鸣源的抑制从 -9.33 dB 削弱到 -2.99 dB ——
**拿 XX-AUDIT-022 那个蜂鸣修复，换 0.35 dB。不改。**

### P1「三套音频栈割裂」—— **坐实，已修**

| 栈 | 走哪 | 受「音乐」开关管吗 |
|---|---|---|
| `core/audio.js` 合成音 + 合成 BGM | `SFX.master` 0.2 / `musicBus` 0.25 | ✅ |
| `xiuxian/ambience.js` 环境音 | 已接 `SFX.musicBus`（XX-AUDIO-004 修过） | ✅ |
| `xiuxian/assets.js` mp3（宿敌 / 越级大佬战 BGM） | **独立的 `<audio>`，`el.volume = 0.42`** | ❌ |

`applySetting('music')` 原来只调 `SFX.setMusic(v)`。mp3 那套跟 `musicBus` 没有任何连线，
所以：**玩家在设置里关掉音乐，宿敌战 / 越级大佬战的 BGM 照播。**

修法（`assets.js` + `main.js`）：

- `assets.js` 新增 `setEnabled()`，`play()` 里在音乐关闭时直接 `stop()`（连 `cur` 一起清，
  否则重新打开音乐会撞上 `if (cur === track) return`，声音再也回不来）
- 每次 `bgm` 事件都按 `Save.data.settings.music` 重新判定 —— 开机时的开关状态靠这条落地

### 新增门禁

| 文件 | 管什么 | 反向注入 |
|---|---|---|
| `tests/audio-level-regression.mjs` | 真跑 `audio.js` 量总线电平：节流不变量 / 不削波且留 ≥3dB / BGM 不盖音效 / lowpass 不遮琶音 | 6/6 变红 |
| `tests/music-toggle-mp3-regression.mjs` | 「音乐」开关必须管到 mp3 那一套（含关开关后重开能恢复） | 4/4 变红 |

`audio-level` 顺带钉了一条**结构性不变式**，比报告设想的削波场景危险得多：

> `play()` 里是 `const gap = GAPS[name] || 0`。
> 只要有一个音效在 `DEFS` 里定义了却**忘了加进 `GAPS`**，
> `gap` 就是 0，那一路**完全没有节流** —— 同帧叠加上限就等于「调用次数」，
> 而且这个洞是静默的。现值 15/15 全覆盖，门禁会守住它。

注入验证：新增一个 `quake` 音效但不给它 GAPS 条目 → 变红。

两条都挂进 `npm test`，`audio-level` 耗时 ~950ms。

**这条门禁自己踩的坑，值得单独记：**

1. **第一版给声源节点也挂了 `gain` Param**（`AudioScheduledSourceNode` 根本没有这个属性），
   空事件 Param 返回当前值 0 → 整条链乘成 0 → `scan()` 恒返 0。
   而 `0 < 1.0` 是**真的** —— 「不削波」那条断言于是一句永远成立的空话，
   报告出来的还是 `-Infinity dBFS`。
   ⇒ 修法是加 `sane()`：**任何测量必须先证明这条总线真的有信号**，
   「量到 0」和「不削波」在数字上长得一模一样。
2. **`bgmLoop(0.25)` 把增益当入参传进去 = 自己抄了一份被测参数**，
   于是把 `audio.js` 的 `musicBus.gain` 从 0.25 改成 0.6 时门禁**照样绿**。
   ⇒ 反向注入当场抓出来。改成省略参数时从 `SFX.musicBus.gain` 读产品现值。
   **门禁要能判产品，就不能自己持有被测的那个值。**
3. 顺手钉了一条产品自身的隐患：`audio.js:73` 和 `:116` 各写了一份 `0.25`
   （init 初值 / `setMusic` 的 ramp 目标）。改一个不改另一个，
   表现是「音乐开关打开后音量莫名变了」。注入验证：只改 ramp 目标 → 变红。

# AUTONOMY.md · 无人值守运转章程

> 这份文件是**开工前必读**。任何设备上的任何 agent（包括子代理）接手任务前先读它。
> owner 已明确授权：**不需要向 owner 汇报过程，做完就测，自己判断，自己往下走。**
> 只在两种情况下停下来找 owner（见 §6「越权红线」）。

---

## 0. 一句话

我们几个设备 + N 个子代理是一个**闭环**：发现问题 → 定性 → 修 → 加门禁 →
反向注入验证 → 提交 → 推送 → CI 终判 → 回报给下一个接手的 agent。
owner 只看**结论**，不看过程。

---

## 1. 组织架构（公司制）

| 角色 | 设备/形态 | 职责 | 不许做 |
|---|---|---|---|
| **统筹（Coordinator）** | 主会话（我） | 派活、收结论、集成、合并、推送、CI 终判 | 不自己埋头改代码超过一轮 |
| **实现（Builder）** | 子代理 worker | 写实现 + 写自己那一个门禁文件 | 不碰别人拥有的文件 |
| **审计（Auditor）** | 子代理 explore / verifier | 只读调查、出带证据的结论 | 不写任何文件 |
| **对端（Peer）** | 锤子 / Z8 侧 | 独立推进 + 通过 `~/agent-room/` 交换 | 不直接改 main（要经统筹） |

**并发上限**：同时最多 4 个子代理。派满之前不要闲置。

---

## 2. 派活规则

统筹在派活时必须写清四件事，缺一不可：

1. **唯一拥有的文件**（不是一个目录，是**具体文件路径**）。文件所有权**互斥**。
2. **可复现的验收判据**（不是「质量高」，是「X 情况下必须报 Y」）。
3. **允许动什么、禁止动什么**（尤其：`js/game/` 只允许加钩子，不得擅自改）。
4. **结论格式**（见 §4）。

### 文件所有权冲突怎么处理

- 两个任务想要同一个文件 → **串行**，不要并行。
- 已经在改 `js/main.js` 的代理没结束前，**任何人不许碰 `js/main.js`**
  （反向注入会临时改它，并发改会互相污染）。
- 代理交付后由**统筹**统一跑测试 + 注册门禁，子代理不许改 `package.json`。

## 3. 验证纪律（本项目铁律，不可协商）

> **度量工具自己出错比没有度量工具更危险。**
> 本项目已累计 30+ 次。下列四条是硬要求：

1. **门禁必须反向注入验证**：故意制造缺陷，确认门禁**真的会红**，然后还原。
   报告里必须写：注入了什么 → 红了几条 → 工作区已还原（附 `git status` 证据）。
2. **门禁必须自检**：任何依赖方向/约定/隐含前提的断言，
   要有一条**反向自检**（把方向写反时，门禁必须报红）。
   —— 实例：我曾把代价轴「损修为」写成剩余比例却按「损掉」判支配，
   结论碰巧成立纯属运气。
3. **假时钟必须响应 `clearTimeout`**：否则回调被调两遍，你在测一个不存在的世界。
4. **DOM 桩必须缓存节点**：`querySelectorAll` 每次返回**同一批活节点**，
   否则你挂的 `onclick` 挂在没人引用的对象上，报出来的红全是假的。

### 判定「门禁有没有效」的标准做法

写完门禁 → 注入一个假缺陷 → 门禁必须红 → 还原。
**门禁在你注入时没红，它就不存在**（哪怕它平时全绿）。

## 4. 结论格式（子代理必须照此交付）

```
1. <结论一句话>
   证据: path:line（必须是行号级的，不是「我搜过了」）
   复现: <可以直接粘到终端跑的命令>
2. ...
———
影响面: <玩家会看到什么 / 什么都不会变>
建议: <最小修法；需要产品决策的，明确写出「需要问什么」>
```

**禁止**：
- 「可能」「也许」「大概」后面不跟证据
- 只报数量不报位置
- 把「我没测出来」说成「不存在」

## 5. 跨设备汇报与决策

### 通道

| 方向 | 机制 |
|---|---|
| 我 → 锤子 | `bash ~/agent-room/to-chuizi.sh < 文件`（投递到对方 `~/FROM-Z8.md`） |
| 锤子 → 我 | 对方写 `~/FROM-Z8.md`，我用 `~/agent-room/fetch.sh` 拉 |

⚠️ **不要用 `report-to-phone.sh`** —— 那是锤子→手机的通道，用错会把消息插回自己收件箱。
（本项目已踩过一次，见 `to-chuizi.sh` 的注释。）

### 什么必须写给对方

- 线上版本号 + CI 终判
- **我碰过的文件清单**（防止两边同时改）
- 已修的 P0 与它们的根因（一句话）
- 我这边**验证过但没修**的发现（对方可能有不同视角）

### 什么不要写给对方

- 没验证的猜测
- 未提交的中间状态

### 合并规矩

- 并发写代码 → 推之前先 `git fetch`，非快进就**合并**，**不许 force push**。
- 冲突只在文档/生成物上时（`version.json` / `TICKETS.md`），
  `version.json` 一律用 `node tests/make-manifest.mjs --write` 重生成，不要手改。
- 合并取舍记 `DECISIONS.md`。

## 6. 越权红线（只有这两种情况停下来找 owner）

1. **需要花掉玩家已有进度**的改动（删档、清空成就、改已发放的奖励）。
2. **不可逆且对外可见**的改动（删分支、删仓库、改线上域名、公开发布敏感内容）。

**除此之外一律自己判断、自己做、自己验证。**
包括但不限于：这些不用问 owner ——
- 战败代价怎么配、文案怎么写
- 某个守卫接不接、作用域是什么
- 版本号升不升
- 一个洞是先修还是先记账

> 判断标准：**能不能用代码/数据/既有设计原则论证清楚。**
> 能论证清楚 → 自己做，做完在 `TICKETS.md` 写清理由。
> 论证不清 → 先记账 + 给出推荐方案 + 推进别的，**不要卡住整条流水线**。

## 7. 每轮固定动作（无人值守循环）

```
1. git fetch + 看远端有没有别人的新提交
2. 从 TICKETS.md 的「仍未修」里取前 4 件，派给 4 个子代理（文件互斥）
3. 收结论 → 独立复核（自己再跑一遍它的复现命令）→ 不符就打回
4. 集成：注册门禁 → npm test + npm run lint → 反向注入抽查
5. 升版 → make-manifest --write → 提交 → 推送
6. CI 终判 → 绿的写进 CHANGELOG，红的**回滚或当场修**，不许改断言凑绿
7. 回报给对端设备 → 回到 1
```

**卡住不许停**：某一件做不了（比如需要实机），就记账并**立刻派下一件**。

## 8. 本机硬约束（别重复踩）

- **没有 chromium**，playwright 装不上 → 所有 L4/视觉只能交 CI 或桌面。
  **严禁尝试安装 playwright。**
- `/tmp` 在 Termux 不可写 → 临时文件一律用 `$HOME`。
- heredoc 会被权限门拦 → 一律用 write 工具写文件。
- GitHub 网络间歇断：`github.com:443` 不通时 `api.github.com` 常常是通的
  （走 Git Data API 直传，方法与坑记在 `PENDING-PUSH.md`）。
- 推 `main` 会触发 CI；推 feature 分支不会。
- **管道退出码陷阱**：`if git push … | tail -2; then echo OK` —— 恒为真，
  失败也报成功。必须写成 `cmd > log 2>&1; rc=$?; [ $rc -eq 0 ] || retry`。
